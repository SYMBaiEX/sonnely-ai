## Data handling

Requests travel over HTTPS to the Sonnely gateway, which reads the prompt to validate and forward the request. The gateway is outside the provider’s trusted execution environment. Sonnely’s ledger records account, model, provider, token, status and charge metadata. Optional chat history lives in the browser and can be cleared in [Settings](/console/settings). See the [Privacy Notice](/privacy) for details.

## Evidence by provider

| Provider | Evidence                                                                                                                                                                                                                 |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| NEAR AI  | Private TEE routes. With a receipt, Sonnely attempts to match NEAR’s ECDSA payload to upstream byte hashes and recover the declared signer. Bind the signer to an attested deployment before relying on hardware claims. |
| Phala    | Sonnely checks the ACI payload and reported route from Phala. Independently check the receipt signature, keyset and hardware evidence when your policy requires it.                                                      |
| Tinfoil  | The Tinfoil SDK verifies the router and encrypts the gateway-to-router request. The customer-to-Sonnely leg uses ordinary HTTPS.                                                                                         |

## Completion receipts

Set `X-Sonnely-Receipt: v1`. The response’s `sonnely_receipt` contains the provider, requested model, provider completion ID, billing reference, charge in millionths of a dollar, and SHA-256 hashes of the upstream request and response. These hashes refer to the bytes exchanged with the upstream provider or SDK. Keep receipts private because hashes can confirm guesses about their contents.

`signature_matched` identifies a NEAR payload and declared signing address match. `aci_payload_matched` identifies Phala’s matched payload and route. `attested_router` identifies Tinfoil’s verified router release. Review the [receipt schema](/api/openapi) for all statuses.
